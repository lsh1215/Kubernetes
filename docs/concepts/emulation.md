# Emulation

## 해결하려던 문제

소프트웨어나 입력이 특정 하드웨어, 운영체제, 장치 인터페이스, 터미널 환경을 전제로 만들어졌는데, 실제 실행 환경에는 그 대상이 없을 수 있다. 이때 원래 대상 없이도 해당 소프트웨어를 실행하거나 테스트하려면 대상의 동작을 다른 환경에서 재현해야 한다.

## 기존 방식의 한계

대상 시스템이 없으면 원래 그 시스템용으로 만들어진 프로그램을 실행할 수 없다. 예를 들어 ARM CPU용 바이너리는 일반적으로 x86 CPU가 직접 실행할 수 없고, 옛 터미널 장비를 전제로 만든 프로그램은 현대 GUI 환경에서 그대로 동작하지 않는다.

## 핵심 아이디어

`emulate`는 어떤 시스템이 다른 시스템의 인터페이스와 동작 의미를 충분히 재현해서, 원래 대상용 프로그램이나 입력이 다른 환경에서도 동작하게 만드는 것이다.

일반어로는 “흉내 내다”에 가깝지만, 컴퓨터 사이언스에서는 보통 “호환 가능한 수준으로 동작을 재현하다”라는 더 강한 의미로 쓰인다.

## 동작 방식

에뮬레이터는 대상 시스템의 입력을 받아 원래 시스템이 했을 법한 동작으로 해석하고 실행한다.

예시:

- CPU 에뮬레이터: 다른 CPU의 명령어 집합, 레지스터, 메모리 접근 의미를 해석해서 해당 CPU용 바이너리를 실행한다.
- 터미널 에뮬레이터: 물리 터미널의 제어 시퀀스와 입출력 동작을 재현해 셸과 CLI 프로그램이 터미널 위에서 실행되는 것처럼 만든다.
- 장치 에뮬레이터: 특정 하드웨어 장치의 인터페이스를 재현해 운영체제나 프로그램이 그 장치가 있는 것처럼 접근하게 한다.

## simulate와의 차이

`simulate`는 어떤 현상이나 상황의 결과를 모델링하는 데 초점이 있다. 반면 `emulate`는 원래 대상용 프로그램이나 입력이 동작할 수 있을 정도의 인터페이스와 동작 호환성에 초점이 있다.

```text
simulate: 어떤 상황/현상을 모델링한다.
emulate: 원래 대상처럼 동작해 기존 프로그램이나 입력을 받아들인다.
```

## Kubernetes와 연결되는 지점

Kubernetes 자체의 핵심 개념은 아니지만, 컨테이너 이미지와 CPU 아키텍처를 공부할 때 연결된다. 예를 들어 ARM용 컨테이너 이미지를 x86 환경에서 실행하려면 QEMU 같은 에뮬레이션 계층이 개입할 수 있다. 이 경우 호스트가 실제 ARM CPU는 아니지만 ARM 명령어를 해석해 ARM용 프로그램이 실행되도록 돕는다.

## 실습으로 확인하기

현재 repository에는 별도 실습을 남기지 않았다. 추후 Docker Desktop, QEMU, `binfmt_misc`, 멀티 아키텍처 이미지를 다룰 때 아래 흐름으로 확인할 수 있다.

```bash
docker buildx ls
docker run --rm --platform linux/arm64 alpine uname -m
docker run --rm --platform linux/amd64 alpine uname -m
```

실제 결과는 호스트 OS, Docker Desktop, QEMU/binfmt 설정에 따라 달라질 수 있다.

## 자주 헷갈리는 점

- 에뮬레이션은 단순히 UI를 비슷하게 만드는 것이 아니라, 원래 대상의 동작 의미를 재현해 호환성을 제공하는 경우가 많다.
- 시뮬레이션은 결과나 현상 모델링에 가깝고, 에뮬레이션은 기존 프로그램이나 입력의 실행 가능성에 더 가깝다.
- 가상화와 에뮬레이션은 겹쳐 보일 수 있지만, 가상화는 보통 같은 종류의 하드웨어 자원을 분리/추상화하는 데 초점이 있고, 에뮬레이션은 다른 시스템의 동작을 재현하는 데 초점이 있다.
